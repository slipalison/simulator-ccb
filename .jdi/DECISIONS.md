D-1 (2026-05-11): Code design = **DDD (Domain-Driven Design)**. Confirmado pelo usuario em /jdi-adopt. Camadas `src/Onboarding.{Domain,Application,Infrastructure,API}` existem mas o pattern dominante eh DDD puro (aggregates ricos, value objects, repositories, exceptions de dominio). Sem rotulo "Clean Architecture" nem "CQRS" como decisao formal — apenas DDD.

D-2 (2026-05-11): Adopted brownfield. Boundary commit hash = **968eefb19dba216d729723e8ffa6a9e166d7698c**. Cobertura 80% enforced APENAS em arquivos novos criados apos este commit. Codigo pre-existente nao eh enforced. Reviewer usa este marker pra distinguir "new" vs "legacy".

D-3 (2026-05-11): OSS-only libraries — todos NuGet packages devem ser MIT/Apache 2.0. Sem MediatR (commercial), sem FluentAssertions (paid). Substitutos: handlers via DI manual (`ICommandHandler<TCommand>` / `IQueryHandler<TQuery, TResult>`), Shouldly em vez de FluentAssertions. Referencia: CLAUDE.md memoria feedback_oss_libraries.md.

D-4 (2026-05-11): Frontend separation architectural constraint — `frontend/client` e `frontend/backoffice` sao projetos totalmente independentes. Sem shared code, sem cross-imports, builds e deploys separados.

D-5 (2026-05-11): Isolamento multi-tenant eh requisito de seguranca de primeira classe. Aggregates company-scoped (Company, Employee, Fundo, ConsultoriaFundo, Custodiante, Cedente) tem HasQueryFilter + ClientId. TipoAtivo eh global (catalogo CVM compartilhado).

D-10 (2026-05-11, Phase 48): Cedente uniqueness COMPANY-SCOPED. Composite unique indexes `(ClientId, Cpf)` para PF e `(ClientId, Cnpj)` para PJ. Empresas diferentes podem ter mesmo CPF/CNPJ independentemente. Preserva isolamento multi-tenant (D-5).

D-11 (2026-05-16, Phase 49): ACF+PKCE eh o auth flow LOCKED para ambos SPAs (`frontend/client` :5173 e `frontend/backoffice` :5174). Sem fallback para implicit/ROPC, sem refatoracao para outro fluxo. Locked desde Phase 33 + MEMORY `feedback_backoffice_auth_ropc`. Toda mudanca preserva PKCE com `code_challenge_method=S256` e secret confidencial do cliente. Cliente legado `onboarding-app` (ROPC public client em `client-realm.json:22-46`) mantido por compat mas marcado para remocao em phase futura — nao bloqueia Phase 49.

D-12 (2026-05-16, Phase 49): Tokens (access + refresh) ficam EXCLUSIVAMENTE em cookies HttpOnly setados server-side pelo handler Vinxi h3 (`auth-server.ts` em ambos SPAs). Proibido escrever access/refresh tokens em `localStorage`, `sessionStorage` ou IndexedDB. Cookies usam `path:"/"`, `httpOnly:true`, `secure:true` em producao (controlado por `NODE_ENV`). Atributo `sameSite` revisado durante o plan (lax vs strict) com seguranca como gate — qualquer afrouxamento exige justificativa em REVIEW.md.

D-13 (2026-05-16, Phase 49): `docker compose down -v` autorizado para reproducao de bug e testing local. Toda mudanca de configuracao Keycloak (clients, redirect URIs, roles, groups, users) DEVE estar persistida em `keycloak/{client,backoffice,master}-realm.json` antes do commit — proibido alterar realm via Admin UI sem refletir no JSON. CI usa apenas o conteudo importado de `keycloak/` na inicializacao do container, entao drift entre instancia rodando e JSON quebra reprodutibilidade.

D-14 (2026-05-16, Phase 49): Usuarios de teste para diagnostico e regressao criados via fixture idempotente — ou bloco `users` adicionado aos realm JSONs existentes, ou script `scripts/seed-test-users.sh` que usa o token client_credentials do service account `onboarding-api-admin` para criar/resetar users determinados. Proibido criar usuarios manualmente em Keycloak rodando sem subsequente persistencia em fixture. Test users tem prefixo `e2e-` no username e password fixo conhecido apenas em ambiente dev.

D-15 (2026-05-16, Phase 49): Gates de seguranca do auth flow sao nao-negociaveis durante a Phase 49. (1) PKCE S256 mantido na request de authorization. (2) Cookies HttpOnly + Secure-em-prod, sem token em storage do browser. (3) CORS allowlist exato em `Program.cs` (sem `*`, sem reflexao de Origin). (4) CSRF protection equivalente a `state` validation no callback + SameSite cookies. (5) `bruteForceProtected:true` em ambos realms preservado. (6) Logout invalida session em Keycloak (end_session_endpoint com `client_id`). Reviewer recusa fix que afrouxe esses guard rails para "fazer funcionar".

D-16 (2026-05-16, Phase 49 reabertura): Workflow de dev local e EXCLUSIVAMENTE `docker compose up`. Proibido rodar `pnpm dev`/`npm run dev` diretamente no Windows host nos diretorios `frontend/client` ou `frontend/backoffice` — cria processo vinxi-host stale que ouve em `[::]:5173`/`:5174` (IPv6) e intercepta requests resolvidos via `localhost`, com fetch upstream para `api:8080` falhando porque host Windows nao acessa a bridge Docker `onboarding-net`. Guard automatico em `scripts/check-dev-env.mjs` invocado via hook `predev` em ambos `package.json` aborta o comando se containers ja estao rodando. Bypass autorizado `ALLOW_HOST_DEV=1` para debugging avancado, documentado em `docs/dev-setup.md`. Detalhamento completo em `.jdi/phases/auth-flow-fix/INVESTIGATION-api-proxy.md`.

D-17 (2026-05-16, Phase 49 reabertura): Playwright configs e quaisquer scripts de teste que disparam fetch contra o stack local DEVEM usar `http://127.0.0.1:PORT`, nunca `http://localhost:PORT`. Elimina ambiguidade IPv6/IPv4 do resolver Windows e garante roteamento para o port mapping do Docker. Aplica-se a `frontend/client/playwright.config.ts`, `frontend/client/pw-no-setup.config.ts`, `frontend/backoffice/playwright.config.ts` e todo spec novo que mencione baseURL.

Refined 2026-05-16 (iter 3): D-17 aplica-se APENAS a `api-proxy.spec.ts` (probes diretos que nao atravessam Keycloak). Auth-flow specs (`auth-flow.spec.ts`, `admin-auth-flow.spec.ts`) ficam em `localhost` para alinhar com os `redirectUris`/`webOrigins` dos realm JSONs do Keycloak que somente contém variantes `localhost`. Usar `127.0.0.1` nos auth-flow specs causava "Invalid state" porque o cookie `pkce_state` era setado na origem `127.0.0.1` mas o Keycloak redirecionava o callback para `localhost`, e o browser nao enviava o cookie cross-origin. Cada project block no Playwright config sobreescreve `baseURL` adequadamente: api-proxy herda `127.0.0.1` do `use` global; auth-flow project blocks definem `baseURL: http://localhost:PORT` explicitamente.

D-18 (2026-05-17, Phase 50): REL-09 (uma única associação ATIVA por par Fundo-Cedente) é enforced em DUAS camadas — partial unique index Postgres `(FundoId, CedenteId) WHERE Status='ATIVO'` + invariante de domínio no aggregate `FundoCedente`. DB é o gate autoritativo contra race condition sob concurrent POST; o domínio lança `DuplicateActiveAssociationException` tipada no fluxo feliz, e o race exception do DB é traduzido para HTTP 409 pelo GlobalExceptionHandler. Defesa em profundidade.

D-19 (2026-05-17, Phase 50): Status da associação é coluna explícita com enum `ATIVO`/`INATIVO`/`HISTORICO`, NÃO derivado da janela de datas. Janela de datas declara vigência; Status registra estado lógico atual. REL-09 partial index usa `WHERE Status='ATIVO'` literal (sem cálculo temporal). Domain pode flagar drift se Status='ATIVO' mas `data_fim < NOW()` em operações de status transition, mas não bloqueia consistência entre os dois campos automaticamente.

D-20 (2026-05-17, Phase 50): Janela de datas é half-open `[data_inicio, data_fim)` com `data_fim` nullable (NULL = vigência infinita); `data_inicio` obrigatório. Aplicável às três associações Fundo↔Cedente, Cedente↔TipoAtivo, Fundo↔TipoAtivo.

D-21 (2026-05-17, Phase 50): Todas três associações N-N do módulo Fundos compartilham o mesmo shape: payload com limites + janela de datas + Status enum. Três aggregates de associação simétricos (`FundoCedente`, `CedenteTipoAtivo`, `FundoTipoAtivo`), três controllers, três sets de migrations. Custo de código compensado por uniformidade arquitetural e auditabilidade idêntica. Reviewer recusa shortcuts que reduzam um dos aggregates a "tag simples" sem janela/limites/status.

D-22 (2026-05-17, Phase 50): Mudança de Status nas associações segue o pattern de state-machine action herdado de D-9 (Phase 48): `POST /api/fundos/{fundoId}/cedentes/{cedenteId}/status` com body `{ NewStatus }`, ActorSub/ActorEmail capturados do JWT, AdminAuditLog registra a transição automaticamente. Mesmo pattern aplicado a `POST /api/fundos/{fundoId}/tipos-ativos/{tipoAtivoId}/status` e `POST /api/cedentes/{cedenteId}/tipos-ativos/{tipoAtivoId}/status`. Transições válidas validadas em invariante de domínio (ex: `HISTORICO` é terminal — não retorna a `ATIVO` sem nova associação).

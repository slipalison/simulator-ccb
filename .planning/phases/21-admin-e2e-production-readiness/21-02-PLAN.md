# Phase 21 — Plan 02: Production Documentation and Deployment Guide

## Objective

Criar documentação completa para operação em produção do sistema de onboarding — desde o deploy inicial até procedimentos de backup, resposta a incidentes, e provisioning de administradores. O objetivo é que qualquer pessoa com acesso ao repositório possa colocar o sistema em produção seguindo os documentos, sem conhecimento prévio do projeto.

## Execution Context

**Strategy:** Doc-first — escrever como se fosse para um operador externo, não para o desenvolvedor original.

**Infrastructure context:** Docker Compose é o ambiente de desenvolvimento. Produção pode ser Docker Compose em VPS, ou migração para Kubernetes/Nitro no futuro.

**Security context:** Keycloak hardened (Phase 2), ROPC grant (documented as deprecated, migration path in PROJECT.md), JWT validation, httpOnly cookies.

**What needs to be added:**
- Deployment guide completo (local → staging → production)
- Admin user provisioning guide (Keycloak setup)
- Backup e restore procedures
- Operational runbook (monitoring, logging, incident response)
- Architecture diagram (visual system overview)
- Environment configuration templates

**What NOT to touch:**
- Backend/frontend code (already production-ready)
- Keycloak realm JSON (already hardened)
- Docker Compose (works for local, production guide will extend it)

## Context

**Current services (compose.yaml):**
- `app_db` — PostgreSQL 16 (application data)
- `keycloak_db` — PostgreSQL 16 (Keycloak internal state, no host port)
- `keycloak` — Keycloak 26.1 (hardened, realm "onboarding")
- `api` — .NET 10 ASP.NET Core (Onboarding.API)
- `frontend-client` — Vinxi SPA (client-facing, port 5173)
- `frontend-backoffice` — Vinxi SPA (admin panel, port 5174)

**Production considerations:**
- HTTPS required (Let's Encrypt / reverse proxy)
- Secrets management (env vars, Docker secrets, or external vault)
- Database backups (pg_dump scheduled)
- Keycloak backups (export/import or db dump)
- Log aggregation (Serilog → OTLP → Grafana LGTM or external)
- Health checks (compose healthcheck → orchestrator)

## Tasks

### Task 1: Deployment Guide
**File:** `docs/DEPLOYMENT.md`

1. Prerequisites: Docker, Docker Compose v2, domain name, SSL certificate
2. Quick start: `docker compose up -d` for local development
3. Staging setup: `.env.staging` with test Keycloak realm, separate DB
4. Production setup:
   - Environment variables (all required vars documented with descriptions)
   - Secrets (JWT signing, Keycloak admin credentials, DB passwords)
   - HTTPS configuration (reverse proxy with Let's Encrypt, or Cloudflare)
   - Docker Compose overrides for production (resource limits, restart policies, logging)
5. Database migrations: `dotnet ef database update` in production
6. Keycloak realm import: first-boot behavior, idempotent re-import
7. Post-deploy verification checklist (all services healthy, can register/login/admin)
8. Rollback procedure (docker compose down, restore previous image, db restore)
9. **Verify:** Follow guide on clean machine, system boots without manual intervention

### Task 2: Admin Role Setup Guide
**File:** `docs/ADMIN-SETUP.md`

1. Overview: How admin roles work in Keycloak (realm roles, `realm_access.roles` in JWT)
2. Creating an admin user:
   - Via Keycloak Admin Console (UI walkthrough)
   - Via Keycloak Admin API (curl/HTTP examples)
   - Via realm import JSON (adding admin role + user to `realm.json`)
3. Assigning the "admin" role: step-by-step with screenshots/diagrams
4. Verifying admin access: login to backoffice, access `/admin/users`, perform CRUD
5. Removing admin access: revoke role, verify 403 response
6. Multiple admins: role-based access control best practices
7. Audit: how admin actions are logged (block/unblock/delete reasons)
8. **Verify:** Create fresh admin user, can access all admin features

### Task 3: Backup & Restore Procedures
**File:** `docs/BACKUP-RESTORE.md`

1. What needs backup:
   - `app_db` (PostgreSQL — client data, registrations)
   - `keycloak_db` (PostgreSQL — Keycloak users, roles, sessions)
   - Keycloak realm export (JSON backup of realm configuration)
2. Backup procedures:
   - `pg_dump` for app_db (schema + data, compressed)
   - `pg_dump` for keycloak_db
   - Keycloak realm export via Admin API
   - Automated backup script (`scripts/backup.sh`)
3. Restore procedures:
   - Stop services (`docker compose down`)
   - Restore app_db from dump (`pg_restore`)
   - Restore keycloak_db from dump
   - Restart services, verify health
   - Keycloak realm re-import if needed
4. Backup testing: restore to separate database, verify data integrity
5. Backup schedule recommendation (daily incremental, weekly full, 30-day retention)
6. **Verify:** Backup → restore cycle completes with zero data loss

### Task 4: Operational Runbook
**File:** `docs/OPERATIONS.md`

1. Health monitoring:
   - `/healthz/live` — liveness probe (is the API process running?)
   - `/healthz/ready` — readiness probe (can API connect to DB and Keycloak?)
   - Docker Compose healthcheck status
   - Grafana dashboards (if LGTM stack deployed)
2. Log access:
   - Structured logs via Serilog (JSON format, TraceId, SpanId)
   - Log aggregation options (stdout → file → Loki → Grafana)
   - How to search logs for a specific user (TraceId correlation)
3. Common incidents and responses:
   - "User cannot login" → check Keycloak user status, check app_db, check token endpoint
   - "Admin 403 error" → verify admin role in Keycloak, check JWT claims
   - "Database connection failed" → check app_db health, connection pool, network
   - "Keycloak unreachable" → check keycloak service, realm import status, bootstrap admin
   - "High memory usage" → check .NET process, EF Core tracking, Vinxi dev mode
4. Maintenance windows:
   - Database migration procedure (downtime, rollback)
   - Keycloak realm update procedure
   - Frontend deployment (zero-downtime with compose)
5. Scaling considerations:
   - Horizontal scaling (multiple API instances behind load balancer)
   - Database read replicas (future)
   - Keycloak clustering (production-hardened mode)
6. **Verify:** Can diagnose and resolve each documented incident using runbook alone

### Task 5: Architecture Documentation

   ```
   Browser → [frontend-client:5173] → [API:5000] → [app_db:5432]
   Browser → [frontend-backoffice:5174] → [API:5000] → [app_db:5432]
   API → [Keycloak:8080] → [keycloak_db:5433]
   ```
2. Service descriptions (purpose, tech stack, ports, dependencies)
3. Data flow diagrams:
   - Registration flow (client → API → app_db → Keycloak)
   - Login flow (client → Keycloak ROPC → JWT → API → profile)
   - Admin flow (backoffice → API → app_db + Keycloak Admin API)
4. Security boundaries:
   - Keycloak hardened config (Phase 2)
   - httpOnly cookies (admin auth)
   - JWT validation (client auth)
   - CORS configuration
5. Database schema overview (Clients, PersonTypes, Cpf/Cnpj, etc.)
6. Key decisions log (reference to PROJECT.md Key Decisions table)
7. **Verify:** New developer can understand system architecture from document alone

### Task 6: Environment Configuration Templates
**Files:** `.env.production.example`, `.env.staging.example`

1. Create `.env.production.example` with all required variables:
   - Database: `POSTGRES_PASSWORD`, `POSTGRES_USER`, `POSTGRES_DB`
   - Keycloak: `KC_BOOTSTRAP_ADMIN_USERNAME`, `KC_BOOTSTRAP_ADMIN_PASSWORD`, `KC_DB_PASSWORD`
   - API: `Jwt__Authority`, `Jwt__Audience`, `ConnectionStrings__DefaultConnection`
   - Frontend: `VITE_API_URL`, `VITE_KEYCLOAK_URL`, `VITE_REALM`
   - Security: `DOTNET_ENVIRONMENT=Production`, cookie secure flags
2. Create `.env.staging.example` with staging-specific values (weaker passwords allowed, but same structure)
3. Document each variable: purpose, format, required/optional, default value
4. Update `.env.example` (local dev) to match current variable names
5. **Verify:** Copy `.env.production.example` → `.env.production`, fill values, `docker compose --env-file .env.production up` boots successfully

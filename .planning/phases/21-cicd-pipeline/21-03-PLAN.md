# Plan 21-03 — Coverage Threshold Enforcement, Cache Optimization, Independent Job Failure Handling

## Overview

Finalize the CI pipeline by hardening the caching strategy, verifying coverage threshold enforcement across all 3 test projects simultaneously, and ensuring independent job failure behavior (each job is a separate quality gate — failure in one does not block or mask failures in others).

This plan also addresses edge cases discovered in research: `coverlet.msbuild` parallel test safety, cache size management, TanStack Router type generation ordering, and integration test container timeouts in CI.

## Success Criteria

1. ✅ Coverage threshold enforcement works correctly across all 3 test projects with `/p:ThresholdStat=total` — aggregate line coverage must be >= 80%
2. ✅ Cache keys are optimized — no false misses, restore keys provide effective fallback
3. ✅ All 3 jobs (backend, frontend-client, frontend-backoffice) are fully independent — no `needs:` between them
4. ✅ Integration tests pass in CI with Testcontainers (PostgreSQL, Keycloak) — no timeout failures
5. ✅ TanStack Router type generation doesn't block `tsc --noEmit` — build order correct
6. ✅ NuGet and npm caches achieve > 80% hit rate on second workflow run
7. ✅ Workflow passes validation with `actionlint` or equivalent YAML validator

## Technical Details

### Coverage Across Multiple Test Projects

The solution has 3 test projects:
- `Onboarding.Domain.Tests` — unit tests for domain value objects and aggregates
- `Onboarding.API.Tests` — unit tests for API controllers, handlers, validators
- `Onboarding.Integration.Tests` — integration tests with real PostgreSQL + Keycloak (via Testcontainers)

When `dotnet test Onboarding.slnx` runs, it executes all 3 test projects sequentially. Coverlet collects coverage from each and aggregates.

**Threshold behavior with `ThresholdStat=total`:**
```bash
# Aggregate coverage across ALL test projects must be >= 80%
dotnet test Onboarding.slnx /p:CollectCoverage=true /p:Threshold=80 /p:ThresholdType=line /p:ThresholdStat=total
```

If Domain tests cover 95% of domain code, API tests cover 70% of API code, and Integration tests cover 60% of infrastructure code — the aggregate must still be >= 80% overall.

**Potential issue:** If current aggregate coverage is < 80%, the CI job will fail immediately. Must verify coverage level BEFORE committing the workflow to `main`.

**Verification command:**
```bash
dotnet test Onboarding.slnx --configuration Release /p:CollectCoverage=true /p:CoverletOutputFormat=cobertura
```
This runs tests and generates coverage WITHOUT threshold enforcement. Review the Cobertura XML or convert to HTML to check current level.

### Cache Key Optimization

**Current key design (from Plans 21-01 and 21-02):**

| Job | Cache Path | Key Pattern | Restore Key |
|-----|-----------|-------------|-------------|
| backend | `~/.nuget/packages` | `${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}` | `${{ runner.os }}-nuget-` |
| frontend-client | `~/.npm` | `${{ runner.os }}-npm-client-${{ hashFiles('frontend/client/package-lock.json') }}` | `${{ runner.os }}-npm-client-` |
| frontend-backoffice | `~/.npm` | `${{ runner.os }}-npm-backoffice-${{ hashFiles('frontend/backoffice/package-lock.json') }}` | `${{ runner.os }}-npm-backoffice-` |

**Why these keys are optimal:**
- `**/*.csproj` matches all C# project files — hash changes only when project references change (not on every code edit)
- `frontend/client/package-lock.json` changes only when npm dependencies change in client
- `frontend/backoffice/package-lock.json` changes only when npm dependencies change in backoffice
- Restore keys (`-nuget-`, `-npm-client-`, `-npm-backoffice-`) provide partial match fallback — even if lockfile hash doesn't match, a previous cache entry is restored (older dependencies, but better than cold start)

**What NOT to cache (confirmed in research):**
- `bin/` and `obj/` — compiled artifacts, cause subtle bugs between builds
- `node_modules` — incompatible with `npm ci`, causes cross-Node-version corruption
- `.vinxi/` and `.output/` — build artifacts, regenerated every run
- Coverage XML files — generated per-run, no value in caching

### Independent Job Failure Behavior

**GitHub Actions parallel job behavior:** When jobs have no `needs:` relationship, they run in parallel on separate `ubuntu-latest` VMs. Each job is an independent quality gate:

- Backend fails, frontends pass → frontends show ✅, backend shows ❌
- Frontend-client fails, others pass → client shows ❌, backend + backoffice show ✅
- All 3 fail → all show ❌ (no masking)

**This is the desired behavior.** No additional configuration needed. The absence of `needs:` between jobs is the mechanism.

**PR behavior:** GitHub blocks merge if ANY required check fails. If branch protection requires "CI" status check, and any of the 3 jobs fails, the PR is blocked.

### Integration Test Containers in CI

`Onboarding.Integration.Tests` uses Testcontainers to spin up PostgreSQL and Keycloak during test execution. In CI:

**Potential issues:**
1. Container startup timeout — slower VMs may take longer to boot
2. Port conflicts — unlikely on isolated GitHub runners, but possible
3. Memory limits — GitHub `ubuntu-latest` has 7 GB RAM. PostgreSQL + Keycloak + .NET test process may approach this.

**Mitigations:**
1. Testcontainers default timeout is 60 seconds. Should be sufficient for PostgreSQL + Keycloak. If not, set `TESTCONTAINERS_CONNECT_TIMEOUT=120` env var in workflow.
2. Testcontainers auto-selects available ports. No conflict risk.
3. Memory: Keycloak image (`quay.io/keycloak/keycloak:26.1`) uses ~512 MB. PostgreSQL uses ~128 MB. .NET test process uses ~256 MB. Total ~900 MB — well under 7 GB limit.

**Workflow env var for CI:**
```yaml
- name: Test with coverage
  env:
    CI: true
    TESTCONTAINERS_CONNECT_TIMEOUT: "120"
  run: dotnet test ...
```

### TanStack Router Type Generation

TanStack Router auto-generates `routeTree.gen.ts` during development (`vinxi dev`). In CI, this file may not exist if it's gitignored.

**Check:** If `routeTree.gen.ts` is committed (not gitignored), `tsc --noEmit` works fine. If it's gitignored, `tsc --noEmit` fails because route types are missing.

**Resolution options:**
1. **Commit `routeTree.gen.ts`** — simplest. The file is auto-generated but committing it means CI can typecheck without running `vinxi dev` first.
2. **Run `vinxi build` BEFORE `tsc --noEmit`** — build generates the route tree, then typecheck validates. Reorders the CI steps.
3. **Add a codegen step** — run `vinxi dev --host 127.0.0.1 --port 3000 &` briefly to generate routes, then kill and typecheck. Too complex.

**Recommended: Option 1.** Check if `routeTree.gen.ts` is in `.gitignore`. If so, remove it from `.gitignore` and commit the file. This is the pattern used by many TanStack Router projects.

If the file is already committed (likely, since the project builds locally), no action needed.

### Workflow Permissions

Top-level `permissions: read-all` sets default for all jobs. Per-job `permissions: contents: read` is explicit and follows least privilege.

```yaml
permissions: read-all

jobs:
  backend:
    permissions:
      contents: read  # checkout + cache
  frontend-client:
    permissions:
      contents: read  # checkout + cache
  frontend-backoffice:
    permissions:
      contents: read  # checkout + cache
```

This prevents accidental writes to the repo from CI. No job needs `contents: write` (no artifact uploads, no PR comments in this phase).

## Risk Assessment

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| Current coverage < 80% — CI fails on first run | Medium | High | Run Task 1 first. If < 80%, either (a) temporarily lower threshold to current level with TODO to raise, or (b) add missing tests before merging CI workflow. Do NOT merge a CI that always fails. |
| `routeTree.gen.ts` not committed — `tsc --noEmit` fails | Medium | Medium | Task 2 catches this. Commit the file or reorder steps (Task 3). |
| Testcontainers timeout in CI — integration tests fail | Low | Medium | `TESTCONTAINERS_CONNECT_TIMEOUT=120` should handle it. If still failing, consider skipping integration tests in CI initially (run only Domain + API tests for coverage). |
| `coverlet.msbuild` file lock issues with 3 test projects | Low | Medium | Running `dotnet test Onboarding.slnx` executes test projects sequentially — no parallel file access. Should be safe. If lock issues arise, add `/p:ExcludeByFile="**/*.gen.cs"` to skip generated files. |
| Cache key hash mismatch — cache never hits | Low | Low | Task 5 validates key patterns. Restore keys provide fallback — even if exact hash misses, a previous cache is restored. |
| `actionlint` not available on Windows dev machine | Medium | Low | Run on WSL, use Docker image (`rhysd/actionlint`), or push to draft PR for GitHub-side validation. |

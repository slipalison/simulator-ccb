    Add login validation schema and API client functions.

    validation-schemas.ts — add:
    ```ts
    export const loginSchema = z.object({
      email: z.string().min(1, "Email é obrigatório").email("Email inválido"),
      password: z.string().min(1, "Senha é obrigatória"),
    });

    ```

    api.ts — add:
    1. `LoginResponse` interface matching backend TokenResponse:
       ```ts
       export interface LoginResponse {
         accessToken: string;
         refreshToken: string;
         expiresIn: number;
         tokenType: string;
         refreshExpiresIn: number;
         scope: string;
       }
       ```

    2. `RefreshTokenRequest` interface:
       ```ts
       export interface RefreshTokenRequest {
         refreshToken: string;
       }
       ```

    3. Error classes:
       ```ts
       export class LoginError extends Error {
         constructor(message: string) { super(message); this.name = "LoginError"; }
       }
       export class RefreshTokenError extends Error {
         constructor(message: string) { super(message); this.name = "RefreshTokenError"; }
       }
       ```

    4. `loginClient(email, password)`:
       - POST to `/api/auth/login`
       - Headers: { "Content-Type": "application/json" }
       - Body: { email, password }
       - On 200: parse and return LoginResponse
       - On 422: throw LoginError("Validation failed")
       - On 401: throw LoginError("Invalid credentials.")
       - On other: throw ApiError("An unexpected error occurred.")

    5. `refreshToken(refreshToken: string)`:
       - POST to `/api/auth/refresh`
       - Body: { refreshToken }
       - On 200: parse and return LoginResponse
       - On 401: throw RefreshTokenError("Invalid or expired refresh token.")
       - On other: throw ApiError("An unexpected error occurred.")

    What to avoid:
    - Don't store tokens in api.ts — that's AuthContext's job
    - Don't call Keycloak directly — backend handles ROPC exchange
    - Backend uses camelCase (accessToken, not access_token) — confirmed in Phase 6 summary
  </action>

<task type="auto">
  <name>Task 2: Create AuthContext for in-memory token storage</name>
  <files>frontend/src/lib/auth-context.tsx</files>
  <action>
    Create a React Context that holds auth state with tokens stored in memory.

    ⚠️ CRITICAL DESIGN DECISION — Module-level token storage (NOT useState):
    Tokens must be stored in a module-level `let` variable, NOT in React useState.
    This prevents tokens from appearing in React DevTools and avoids stale closure bugs.

    ```ts
    // Module-level — OUTSIDE any component, NOT in useState
    interface AuthTokens {
      accessToken: string | null;
      refreshToken: string | null;
      expiresAt: number | null;
      refreshExpiresAt: number | null;
    }
    let tokens: AuthTokens = { accessToken: null, refreshToken: null, expiresAt: null, refreshExpiresAt: null };
    ```

    AuthContext exports:
    - `AuthProvider` — wraps children, manages state
    - `useAuth()` — hook to access context

    Derived state (useState — OK for booleans):
    ```ts
    const [isAuthenticated, setIsAuthenticated] = useState(false);
    const [isLoading, setIsLoading] = useState(false);
    ```

    Context value:
    ```ts
    interface AuthContextValue {
      auth: { isAuthenticated: boolean; isLoading: boolean };
      login: (email: string, password: string) => Promise<void>;
      logout: () => void;
      refreshIfNeeded: () => Promise<void>;
      getAccessToken: () => string | null;
    }
    ```

    Implementation:
    - `login(email, password)`: calls loginClient, writes to module-level `tokens` variable, sets `setIsAuthenticated(true)`
    - `logout()`: resets module-level `tokens` to all null, `setIsAuthenticated(false)`
    - `getAccessToken()`: returns `tokens.accessToken` (reads from module-level variable — no stale closure risk)
    - `refreshIfNeeded()`: if access token is near expiry (< 60s), calls refreshToken API and updates module-level tokens
    - NEVER writes to localStorage, sessionStorage, or cookies — memory only
    - On page refresh (F5), module-level variables are destroyed — user must re-login (correct behavior per SEC-10)
    - Wrap in `useContext` with error if context is null

    What to avoid:
    - DO NOT use useState for tokens — only for derived state (isAuthenticated, isLoading)
    - Don't persist tokens anywhere — memory only (SEC-10)
    - Don't auto-refresh on mount — user must log in first
    - Don't redirect on login — that's LoginPage's job
    - Don't fetch /api/clients/me here — that's Profile UI's job (Phase 10)
  </action>
  <verify>
    1. npx tsc --noEmit passes
    2. AuthProvider wraps children without error
    3. useAuth() returns login function and isAuthenticated=false initially
    4. Module-level `tokens` variable exists (NOT useState for tokens)
    5. getAccessToken() reads from module-level variable — no stale closure
  </verify>
  <done>AuthContext provides login(), logout(), refreshIfNeeded() with memory-only token storage (module-level let, NOT useState)</done>

# Plan 26-02 — TruffleHog Active Verification + SARIF Export + Secrets Incident Response Documentation

## Overview

Integrate TruffleHog into the CI pipeline for active secret verification. Unlike Gitleaks (pattern matching), TruffleHog verifies if detected secrets are actually active/valid by attempting to authenticate with them. This eliminates false positives from expired or dummy credentials. Also create `docs/secrets-incident-response.md` documenting the process for revoking and rotating compromised keys.

## Success Criteria

1. ✅ `secrets-trufflehog` job in `ci.yml` runs `trufflehog filesystem --directory . --only-verified`
2. ✅ Scan fails if ANY verified (active) secret is found
3. ✅ SARIF results uploaded via `github/codeql-action/upload-sarif@v4` with `category: trufflehog`
4. ✅ `docs/secrets-incident-response.md` documents: secret revocation process, key rotation procedure, escalation path
5. ✅ TruffleHog uses `trufflesecurity/trufflehog@main` (official action)
6. ✅ Git history scanning enabled (not just current commit)

## Scope

### In Scope
- `secrets-trufflehog` job in `.github/workflows/ci.yml`

## Technical Details

### CI Job

```yaml
secrets-trufflehog:
  name: Secrets — TruffleHog
  runs-on: ubuntu-latest
  permissions:
    contents: read
    security-events: write
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0  # Full git history

    - name: Run TruffleHog
      uses: trufflesecurity/trufflehog@main
      with:
        extra_args: --only-verified --fail --json

    - name: Upload TruffleHog SARIF
      if: always()
      uses: github/codeql-action/upload-sarif@v4
      with:
        sarif_file: results.sarif
        category: trufflehog
```

### TruffleHog vs Gitleaks Comparison

| Aspect | Gitleaks (26-01) | TruffleHog (26-02) |
|--------|------------------|---------------------|
| Detection | Pattern matching | Pattern + active verification |
| False Positives | Higher (matches any pattern) | Lower (verifies credentials work) |
| Speed | Fast (regex only) | Slower (HTTP auth attempts) |
| Use Case | Pre-commit, CI gate | CI verification layer |
| Custom Rules | Yes (`.gitleaks.toml`) | Limited (built-in detectors) |

### `docs/secrets-incident-response.md` Structure

1. **Detection**
   - How secrets are detected (Gitleaks + TruffleHog)
   - Alert channels (GitHub Security Tab, CI failure)

2. **Immediate Response (0-1 hour)**
   - Identify the secret type (DB password, API key, JWT secret, Keycloak secret)
   - Revoke the compromised credential immediately
   - Document the finding (file, commit, author, time)

3. **Rotation Procedure (1-24 hours)**
   - Database passwords: Generate new password, update `.env` and Keycloak/infrastructure
   - API keys: Create new key in provider, update application config, revoke old key
   - JWT secrets: Generate new signing key, redeploy API, update all clients
   - Keycloak secrets: Regenerate client secret in Keycloak admin, update API config

4. **Post-Incident (24-48 hours)**
   - Root cause analysis: How was the secret committed?
   - Prevention: Add rule to Gitleaks if not already covered
   - Team notification: Share lessons learned
   - Update `.gitleaksignore` if false positive

5. **Escalation Path**
   - Level 1: Developer who committed the secret
   - Level 2: Tech lead / security champion
   - Level 3: CTO / security team (if production credentials exposed)
